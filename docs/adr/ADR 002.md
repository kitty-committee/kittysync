# Application Stack

## Context and Problem Statement

This is an enterprise-grade application, thus it must provide exceptional reliability, availability and security. What libraries and frameworks should be chosen to support these requirements while playing to the team's strengths?

## Decision Drivers

### Reliability and Integrity

- The application must gracefully degrade: if a service fails, the application must still be usable with minimal loss of functionality.
- User submissions must not be lost, even across client crashes, network drops or server restarts.
- Strong static type checking and linting to catch the most common of bugs.

### Availability and Scalability

- There must be no single point of failure in the application.
- Horizontal scaling of backend, including Websocket connections.

### Security and Compliance

- Data in transit must be encrypted (TLS).
- XSS and CSRF protection features.
- Libraries must have a process for tracking CVEs and supply-chain risks.

### Team and Organisational

- Team familiarity with Java, JavaScript, Python and Svelte.
- Small team size requires less diverse language choices, as individuals will frequently work on all parts of the application.

### Ecosystem and Sustainability

- Library and feature maturity and number of maintainers.
- Libraries must have a permissive license compatible with commercial distribution.
- Example of production usage at a similar scale.

## Considered Options

### Frontend

- SvelteKit
- React
- SolidJS

### Backend

- SvelteKit
- Python + Flask
- NodeJS + Express
- NodeJS + Fastify

### Realtime Communication

- Sockets.io backend
- Separate WebSocket server
- Integrate WebSockets with backend

### Availability

- Single backend
- Sharded backend + Editing traffic routed to single node
- Sharded backend + Inter-node communication over WebSocket
- Sharded backend + Inter-node communication through Redis

## Decision Outcome

### Frontend

Chosen option: SvelteKit due to the team's familiarity with it, its maturity and deep integration with TypeScript.

#### Consequences

- The team needs to accommodate a build step in the frontend development workflow.
- The smaller ecosystem may limit access to libraries and components.

### Backend

Chosen option: NodeJS + Fastify because it is mature, fast, has built-in TypeScript integration and a rich plugin ecosystem.

#### Consequences

- The team will need to learn Fastify and its plugin ecosystem.
- Not using SvelteKit as a backend increases complexity and creates prerendering pitfalls.

### Realtime Communication

Chosen option: Integrated WebSocket server due to the lower operational complexity.

#### Consequences

- WebSocket functionality will be handled by the same package as the backend, increasing its complexity.

### Availability

Chosen option: Sharded backend + Inter-node communication through Redis because it allows for simple horizontal scaling.

#### Consequences

- Redis becomes another layer in the stack and a dependency that must be operated and monitored.

## Pros and Cons of the options

#### SvelteKit

- Pro: It integrates with CI tools well.
- Pro: It has a smaller bundle size than alternatives.
- Pro: Team familiarity.
- Con: It has a smaller ecosystem than the alternatives.
- Con: It adds a build step to the frontend.

#### React

- Pro: It has the largest ecosystem of the alternatives.
- Con: It has a larger bundle size.
- Con: Team unfamiliarity.

#### SolidJS

- Pro: Excellent fine-grained reactivity.
- Con: It has the smallest ecosystem of the alternatives.

#### Python + Flask

- Pro: Team familiarity.
- Con: The operational complexity of using two different languages.

#### NodeJS + Express

- Pro: It is ubiquitous and well documented.
- Con: It has weaker TypeScript support.

#### NodeJS + Fastify

- Pro: It is mature, fast, has built-in TypeScript integration, and a rich plugin ecosystem.
- Pro: It has a WebSocket plugin for the integrated WebSocket server.
- Pro: It is a simple NodeJS application without any build step.
- Pro: One single language for the entire application simplifies CI/CD checks.
- Con: The team is unfamiliar with it.

#### Single backend

- Pro: It has less operational complexity.
- Con: It is only vertically scalable.

#### Sockets.io backend

- Pro: It has fallback to HTTP polling if the client does not support WebSockets.
- Pro: It handles reconnecting the client if the server disconnects.
- Con: It adds unnecessary operational complexity.

#### Integrated WebSocket server

- Pro: It has lower operational complexity than using multiple separate solutions.
- Con: WebSocket functionality must be implemented and maintained within the backend.

#### Sharded backend + Editing traffic routed to single node

- Pro: It keeps the stack small.
- Con: It requires use of logic at the load balancing level.

#### Sharded backend + Inter-node communication over WebSocket

- Pro: It keeps the stack small.
- Con: It adds more operational complexity in the inter-node protocol and session detection logic.

#### Sharded backend + Inter-node communication through Redis

- Pro: There is no added operational complexity for traffic routing.
- Pro: It allows for simple horizontal scaling.
- Con: It adds another layer to the stack.

## AI Prompt Appendix

### Frontend

```
We have been tasked with making an enterprise-grade real-time markdown collaboration and editing web application. We are trying to decide on a frontend framework, our team has some experience with Svelte but would like to hear our options before we decide.
```

The AI offered a lot of advice regarding framework support WYSIWYG (what you see is what you get) editors which are not applicable for this markdown editor. It also offered advice regarding hiring team members and for the most part suggested that we use Svelte purely for our experience with it.

### Backend

```
We have been tasked with making an enterprise-grade collaborative markdown editor for a University project. We have decided on a NodeJS based backend, but would like advice picking which web framework to use. We will require websocket support as a part of the backend, if that is integrated using the Node framework or a reverse proxy is undecided. We also would like to design a system with high availability using a load balancer and our choice of framework should support this.
```

The AI offered detailed advice weighing up four web frameworks. It once again mentioned WYSIWYG editor integration and real-time concurrently architectural design decisions (see ADR 001), including prebuilt backends such as Hocuspocus. The AI also gave insight into strategies for horizontal scaling, such as using Redis or cross-instance messaging. This was extremely helpful for designing our backend architecture.

```
So if you use Redis for cross-instance messaging, is the idea that all instances will talk to a single Redis instance for state synchronisation using pub/sub? Is it okay to use just a single Redis instance? What if that instance goes down?
```

The AI gave great insight on running a highly available Redis swarm and designing the backend with graceful degradation in mind.
